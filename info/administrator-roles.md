# Перший адміністратор і суміщення прав

## Узгоджені правила

- Код адміністратора доступний лише до появи першого адміністратора в БД. Для початкової реєстрації потрібні email із `ADMIN_EMAILS` і правильний `ADMIN_REGISTRATION_TOKEN`.
- Коли адміністратор уже існує, усі нові облікові записи реєструються як викладачі зі статусом очікування. Прихований або повторно надісланий код не надає прав.
- Адміністратор може призначити іншого схваленого користувача адміністратором і повернути призначеному адміністратору роль викладача.
- Адміністратор, створений через початковий код, захищений від пониження. Чинні адміністратори старої версії також отримують захист: до цієї зміни їх можна було зареєструвати лише через код.
- Адміністратор зберігає всі викладацькі можливості для власних занять, студентів, імпорту й журналу. Адміністративні права додаються до них.

## План і погоджені межі тестування

Користувач погодив перевірки реєстрації, керування ролями та викладацьких функцій адміністратора.

- [x] Спільні викладацькі можливості й адміністративне меню.
- [x] Атомарна початкова реєстрація, зокрема паралельні запити.
- [x] Збереження ознаки захищеного адміністратора та міграція наявних облікових записів.
- [x] Призначення/пониження ролей із перевіркою прав на сервері.
- [x] Форма реєстрації та сторінка керування користувачами.
- [x] Ізольовані інтеграційні перевірки, браузерний сценарій, typecheck і production build.

Тести з БД виконуються лише в тимчасовій схемі з окремою роллю без прав запису в робочі таблиці. Production-акаунти не використовуються як тестові. Дизайн-аудит не проводиться відповідно до вказівки користувача.

## Реалізація й перевірки

- `008_administrator_bootstrap.sql`: незмінна ознака `is_bootstrap_administrator`, перевірка узгодженості ролі й схвалення, захист через тригер. Міграцію застосовано 27.08.2026: одна наявна адміністративна обліковка отримала захист, без зміни пароля, сесій або навчальних даних.
- Початкова реєстрація та зміна ролей використовують одне транзакційне блокування й `ReadCommitted`; повторна перевірка виконується після отримання блокування. Два паралельні запити не створюють двох початкових адміністраторів.
- Форма отримує лише ознаку відкритої початкової реєстрації, без коду або списку дозволених адрес. Старе відкрите вікно не дає змоги обійти серверну перевірку.
- Роль читається із БД під час перевірки сесії. Після пониження новий запит більше не має адміністративного доступу, але зберігає викладацький.
- `attendance-runner.mjs --administrators`: неправильний код, паралельна початкова реєстрація, повторний код, pending-користувач, підроблена роль/актор, захищений адміністратор, призначення/пониження, чинні сесії, власні студенти, заняття, імпорт і журнал — пройдено.
- `administrator-migration-check.mjs`: перенесення старого адміністратора, заборона пониження/зняття захисту/блокування/видалення на рівні БД, повторне застосування без захисту призначених адміністраторів — пройдено.
- Попередні інтеграційні сценарії журналу та груп — пройдено.
- Браузер: до першого адміністратора поле коду є, після його створення — відсутнє; реєстрація початкового адміністратора, захищена позначка, призначення/пониження/повторне призначення через «Користувачі», вхід призначеним адміністратором, додавання студента, створення власного заняття та збереження відвідування — пройдено. Серверні відповіді 200, нових помилок і попереджень у browser console немає.
- 112 звичайних тестів пройдено; три мережеві сценарії пройдено окремо в ізоляції. TypeScript і production build пройдено. Тимчасові схеми та ролі видалено.
- Код у цьому етапі не публікувався на production; для появи нового інтерфейсу на домені потрібні commit, push і deployment.

Команди виконуються з `node --env-file=.env.local info/testing/…`. Звичайний `pnpm test` пропускає три мережеві сценарії без спеціальної ізольованої схеми.
