# Автентифікація та розмежування доступу

## Поточний стан

- Автентифікацію надає Clerk, підключений до Vercel-проєкту як ресурс `vidmitka-auth`.
- Публічні сторінки доступні без входу: головна сторінка та загальний розклад.
- Приватний кабінет доступний лише автентифікованому й схваленому користувачу.
- Адміністративні сторінки додатково перевіряють роль на сервері.
- Адміністратор зі списку `ADMIN_EMAILS` схвалюється автоматично.
- Новий викладач після реєстрації очікує схвалення адміністратора.
- Інтерфейс і вбудовані форми Clerk локалізовані українською мовою.

## Визначення ролі

Роль визначається за primary email, який повертає Clerk:

1. Значення `ADMIN_EMAILS` розбирається як перелік адрес через кому, крапку з комою або пробільні символи.
2. Адреси нормалізуються: пробіли видаляються, регістр не враховується.
3. Точний збіг із переліком надає роль адміністратора.
4. Автентифікований користувач без збігу отримує роль викладача.

Безпечне значення за замовчуванням — викладач. Відсутня або порожня змінна `ADMIN_EMAILS` не створює адміністратора.

## Схвалення облікового запису

1. Після завершення реєстрації система визначає роль за primary email.
2. Адміністратор одразу отримує доступ незалежно від metadata акаунта.
3. Новий викладач отримує статус `pending` і бачить сторінку очікування замість приватного кабінету.
4. Адміністратор відкриває розділ «Викладачі» та виконує дію «Схвалити доступ».
5. Система записує в Clerk private metadata значення `approved: true`, час схвалення та ідентифікатор адміністратора.
6. Після повторної перевірки статусу викладач отримує доступ до рольового меню й приватних маршрутів.

Дані схвалення є серверними: користувач не може самостійно змінити private metadata з браузера. Адміністративна Server Action перед записом повторно перевіряє роль поточного користувача та роль цільового акаунта.

## Межі доступу

| Розділ | Без входу | Викладач | Адміністратор |
| --- | --- | --- | --- |
| Головна сторінка | так | так | так |
| Загальний публічний розклад | так | так | так |
| Огляд кабінету | ні | лише після схвалення | так, автоматично |
| Розклад у кабінеті | ні | лише після схвалення | так, автоматично |
| Мої заняття | ні | лише після схвалення | ні, окремий пункт не показується |
| Створення заняття | ні | після схвалення, для себе | так, із вибором викладача після наповнення довідника |
| Профіль | ні | так | через меню облікового запису |
| Викладачі, предмети, аудиторії, налаштування | ні | ні | так |

Приховане посилання не є перевіркою безпеки. Адміністративний layout повторно перевіряє роль на сервері перед відображенням сторінки. Подальші операції запису мають так само перевіряти користувача й право на конкретний ресурс безпосередньо в серверному сценарії.

## Локальне налаштування

Vercel CLI зберігає інтеграційні ключі у `.env.local`, який не комітиться. Власний локальний список адміністраторів слід записати в `.env.development.local`:

```dotenv
ADMIN_EMAILS=admin@example.com,second-admin@example.com
```

Після зміни env-файлу потрібно перезапустити локальний dev server.

## Налаштування Vercel

Для production, preview та development змінну `ADMIN_EMAILS` потрібно додати в налаштуваннях Environment Variables Vercel. Наразі вона налаштована як sensitive-змінна в усіх трьох середовищах. Значення може відрізнятися між середовищами. Після зміни production-значення потрібен новий deployment.

Секретні ключі Clerk, Neon або інші приватні значення не можна додавати до Git. Файл `.env.example` містить лише назви та безпечні приклади маршрутів.

## Відоме обмеження поточного етапу

Розділи довідників і занять уже мають правильні межі доступу та рольові меню, але операції з даними ще не підключені до фізичної схеми БД. Форми й порожні стани позначають це прямо, не імітуючи успішне збереження.
