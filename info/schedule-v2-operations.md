# Експлуатація розкладу v2

## Статус

Документ описує реалізований пакет VID-029. Автоматичні тести, typecheck, production build, браузерний QA, міграції, імпорт, commit, push і deployment для цього пакета ще не запускалися. До `PASS` незалежного QA це інструкція для локального / тестового середовища, а не підтвердження production-готовності.

## Основні маршрути

- `/schedule` — публічний розклад: група, дата, день / тиждень, актуальний тип навчального тижня й позначки винятків;
- `/transfers` — публічні переноси, заміни та скасування;
- `/admin/login` — єдина форма входу, якої немає в публічній навігації;
- `/admin` — захищена головна адмін-панель;
- `/admin/schedule`, `/admin/exceptions`, `/admin/import`, `/admin/week-settings` — основні робочі сценарії;
- `/admin/groups`, `/admin/disciplines`, `/admin/lesson-types`, `/admin/rooms`, `/admin/teachers`, `/admin/periods` — довідники.

## Міграція

1. Створити резервну копію / branch тестової Neon БД.
2. Заповнити `DATABASE_URL_UNPOOLED` або `DATABASE_URL` у `.env.local`.
3. Виконати `pnpm db:migrate`.
4. Перевірити наявність запису `014_schedule_v2.sql` у `schema_migrations`.

Міграція additive-first: створює нові таблиці й не видаляє старі таблиці студентів, журналу чи старих занять. Їхній код вилучено з робочого застосунку, але дані залишаються rollback-страхуванням до окремого дозволеного архівування.

## Створення адміністратора

У `.env.local` додати, не комітячи значення:

```dotenv
ADMIN_EMAIL=admin@example.edu
ADMIN_NAME=Адміністратор розкладу
ADMIN_PASSWORD=НадійнийПароль1!
```

Після міграцій виконати `pnpm admin:init`. Команда створює або оновлює лише схваленого адміністратора, використовує scrypt із випадковою сіллю, скидає блокування входу й ніколи не друкує пароль у лог.

## Імпорт JSON

1. Авторизуватися через `/admin/login`.
2. Відкрити `/admin/import`.
3. Обрати `data/teacher-schedule-lessons.json` і натиснути «Перевірити файл».
4. Переглянути помилки рядків, відсутні номери пар і попередження про конфлікти.
5. Якщо попереджень немає — підтвердити імпорт; якщо є — поставити явну позначку підтвердження й повторно обрати файл, якщо браузер очистив file input.

Файл обмежено 5 МБ і 10 000 записів. Запис виконується атомарною Serializable-транзакцією. `source_id` стабільний для конкретної дати / пари / викладача / груп / джерельного дня-тижня; `source_payload_hash` дозволяє оновити виправлену дисципліну, аудиторію або тип без дублювання.

Кожен валідний рядок створює базовий повторюваний запис у `schedule_entries`: діє з дати `date`, у вказаний `dayOfWeek` і `weekType`, до 31 грудня того самого року. Повторний імпорт оновлює або пропускає той самий `source_id`. Старі імпортовані `one_time`-винятки переносяться до базових записів і позначаються `superseded`; до повторного імпорту public resolver читає їх у сумісному режимі без службових позначок.

## Формування фактичного розкладу

`getPublicScheduleDay`:

1. визначає чисельник / знаменник централізованим календарем;
2. відбирає активні базові записи за днем, тижнем, групою й межами дії;
3. застосовує найновіший активний виняток початкової дати;
4. не показує старий екземпляр перенесеного заняття;
5. додає перенесені на обрану дату й разові заняття;
6. сортує результат за фактичним часом.

## Перевірки перед релізом

Незалежний QA-агент повинен виконати щонайменше:

```powershell
pnpm exec tsc --noEmit
pnpm test
pnpm build
```

Додатково потрібні ізольована тестова міграція, імпорт наданого JSON двічі, перевірка rollback критичної помилки, браузерні сценарії публічного розкладу й `/admin`, console, клавіатура, overflow та 1440 / 820 / 390 px. Production-міграція й deployment — лише після актуального `PASS` і окремого дозволу.

Ізольований DB/integration-прогін створює випадкову схему `qa_vid029_*`, перевіряє її через `current_schema()`, двічі застосовує міграцію 014, виконує CRUD / імпорт / rollback / resolver і видаляє тільки цю схему:

```powershell
pnpm test:schedule-v2-integration
```

Для браузерного QA після `pnpm build` можна підняти production server на порту 3013 з тією самою тимчасовою моделлю даних. Після зупинки процесу схема видаляється автоматично:

```powershell
node --env-file=.env.local scripts/with-isolated-schedule-v2-db.mjs pnpm start --port 3013
```

## Відомі межі до QA

- Старі таблиці даних не видалені навмисно; потрібна окрема резервна копія й руйнівна міграція після стабілізації v2.
- Конфлікти наданого датованого JSON показуються як попередження, бо частина з них може описувати підгрупи або спільні заняття.
- Публічний schedule API повертає тільки поля відображення; адміністративні зміни виконуються захищеними Server Actions, а не відкритими Route Handlers.
