# Пакетний QA Vidmitka

## Домовленість від 28.08.2026

Під час розробки накопичуємо зміни й ведемо [журнал задач](../tasks.md). Не запускаємо тести, збірку чи браузерну перевірку після кожної правки. Основний агент реалізує; окремий QA-агент незалежно перевіряє завершений пакет, класифікує запити й організовує перевірки.

Запуск відбувається за запитом користувача на тестування або перед дозволеним релізом. «Додай», «виправ», «далі» та закінчення відповіді не є командами запустити QA. «Перевір», «запусти QA», «протестуй пакет», «деплой» або «залий у main» запускають фінальну фазу для відповідного обсягу. Запит лише на пояснення не стає новою задачею на реалізацію.

Додаткове погодження від 28.08.2026: реалізація поставлених задач, вибір TDD-меж і підготовка поведінкових тестів дозволені без повторних процедурних запитів. QA сам визначає потрібні перевірки в узгодженому обсязі. Цей дозвіл не змінює пакетного режиму запуску та не дозволяє публікацію або зміну робочих даних.

Це керований Codex процес у поточній задачі, не фоновий сервіс, cron чи встановлений AI-job у CI. Нативні Vercel-перевірки залишаються активними. Перед push у `main` потрібен QA, оскільки цей push запускає deployment.

## Життєвий цикл задач

- Основний агент реєструє запит, попередній тип, критерії приймання, пов'язані файли й стан розробки.
- QA підтверджує класифікацію на початку фінального прогону: **баг**, **фіча** або **технічна задача**. Вказує причину, спираючись на запит і чинні вимоги.
- Стан розробки: **Заплановано → У роботі → Реалізовано**. Після зауважень — **Потребує виправлень**; після дозволених виправлень — знову **Реалізовано**.
- QA-стан: `NOT_RUN` (очікується), `PASS` (підтверджено), `FAIL` (дефект), `BLOCKED` (бракує середовища, доступу чи однозначної вимоги). Не плутати з результатом окремої команди.
- **Виконано** можна ставити лише після `PASS`; **Опубліковано** — лише після фактичної перевірки deployment. Реалізація без QA не є релізом.
- Новий запит отримує наступний `VID-NNN`; уточнення доповнює той самий запис. Старі результати не видаляються, а нові критерії скидають актуальний QA-стан.

## Передача пакета окремому агенту

Основний агент читає `.agents/skills/qa-batch/SKILL.md`, заповнює [доручення](handoff-template.md) і запускає одного QA-субагента. Самоперевірка автора не замінює цей етап. Незалежне делегування за інструкціями AGENTS.md підтримує [офіційна документація Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Модель вибирає основний агент: зазвичай `gpt-5.6-terra` / `high`; для ролей, автентифікації, міграцій і складних ризиків — `gpt-5.6-sol` / `high`. Це проєктна політика вибору з доступних у поточній сесії моделей, а не обіцянка конкретної вартості або якості. Орієнтир — [OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model).

Доручення містить первинні запити, критерії, ID задач, межі diff і дозволи. У ньому не повинно бути висновку «все виправлено, підтвердь». QA читає фактичний код і сам встановлює результат. Під час перевірки основний агент не редагує код чи тести пакета; може готувати текст релізу.

QA може записувати звіт, результати задач і необхідні тестові сценарії. Він не виправляє продукт, не публікує, не змінює ролі реальних користувачів та не застосовує production-міграції. Якщо незалежне делегування недоступне — `BLOCKED`, не автоматичний `PASS`.

## План і виконання перевірок

QA один раз оцінює весь пакет і записує план у майбутньому звіті:

1. Зіставити запити з реалізацією. Для багу перевірити сценарій помилки та близьку регресію; для фічі — нову поведінку, помилкові дані й права ролей; для технічної задачі — відповідні артефакти й узгодженість правил.
2. Для зміненого коду застосунку виконати `pnpm exec tsc --noEmit`, `pnpm test`, `pnpm build`; доступний lint — якщо команда існує. Не повторювати повний набір на кожен файл чи кожну задачу пакета.
3. Запустити релевантні DB integration-сценарії через `info/testing/attendance-runner.mjs`: без параметрів — журнал; `--groups` — групи; `--administrators` — ролі/реєстрація; `--rooms` — аудиторії; `--calendar` — відпрацювання; `--upcoming` — типи й найближчі заняття; `--periods` — кольори пар та їх адміністрування. `pnpm test` без спеціального середовища пропускає ці сім сценаріїв, що не означає їх проходження. VID-003 і VID-006 змінюють спільні записи занять/журналу, тому потребують також регресій календаря, журналу, груп і викладацьких дій адміністратора. VID-007 потребує перевірки первинної/повторної міграції кольорів на фіктивних старих записах, прав, незмінних часових конфліктів і живої шкали в браузері; harness підготовлений для 011, production-міграцій у QA немає.
4. Для зміненого UI пройти головні сценарії в реальному браузері, перевірити ролі, клавіатуру, console і overflow. UI-пакет перевірити на 1440, 820 та 390 px; для відступів використати `ui-spacing-review`. Не перетворювати функціональний QA на непогоджений редизайн.
5. Якщо пакет містить лише документацію/скіли без змін застосунку, перевірити їхню структуру, посилання та узгодженість; application checks позначити `N/A` з обґрунтуванням. Непідготовлені або недоступні обов'язкові перевірки — `BLOCKED`, не `N/A`.

Перед виконанням QA сам читає повні інструкції потрібних навичок. Наявні `webapp-testing` / `playwright` — інструменти виконання, а `qa-batch` визначає **коли**, **ким** і **для якого пакета** вони використовуються. Для in-app browser діють інструкції його окремого skill.

## Безпека тестових даних

Локальні env-файли можуть вести до тієї самої БД, що й production. Не робити висновок про безпечність БД з назви `.env.local`.

Використовувати ізольовану схему й окрему роль існуючого test harness, фіктивні акаунти та перевірку заборони змін робочих таблиць. Для локальної production-перевірки після build доступні `--rooms --browser --production`; завершення — команда `stop` у власному процесі. Після прогону прибрати тільки власне тестове середовище. Не записувати секрети або реальні персональні дані в журнал, звіти, промпт агента чи скриншоти.

Не повторювати записи «наосліп» після мережевого тайм-ауту: спочатку перевірити результат. Інфраструктурну помилку відокремити від багу продукту. Якщо суттєву перевірку неможливо завершити — описати причину й поставити `BLOCKED`.

## Звіт, виправлення та реліз

QA створює `info/qa/reports/QA-YYYYMMDD-NN.md` за [шаблоном](report-template.md), оновлює QA-поля задач і повертає стислий підсумок. Артефакти, якщо потрібні, — `info/qa/artifacts/<batch-id>/`.

У звіті фіксуються дата, ID агента й модель, задачі пакета, commit SHA та фактичний перевірений обсяг. Для dirty worktree недостатньо SHA: додати перелік змінених/untracked файлів і контрольні суми перевірюваних файлів без env/секретів. Для закоміченого пакета — точний commit/diff від релізної бази. Генеровані QA-звіти не входять у відбиток коду; зміна критеріїв чи реалізації робить старий висновок неактуальним для цього обсягу.

Дефект має задачу, пріоритет P0–P3, кроки відтворення, очікуваний і фактичний результат, докази та наслідок для релізу. QA не створює нові продуктові вимоги самостійно.

Після `FAIL` основний агент, якщо реалізація виправлень уже дозволена запитом, виправляє всі узгоджені дефекти пакетом. Потім той самий QA-агент перевіряє виправлений обсяг і потрібні регресії. Не запускати повний прогін після кожного окремого виправлення. Якщо користувач просив лише перевірку — спершу повернути звіт без змін продукту.

Реліз дозволяє лише актуальний `PASS` для всього релізного пакета без невирішених обов'язкових перевірок. `FAIL`, `BLOCKED`, `NOT_RUN` або зміни після перевірки не дозволяють push/deploy. Необов'язкові рекомендації можна винести в backlog; порушений критерій приймання не можна замаскувати рекомендацією. Дозвіл на QA сам по собі не дозволяє публікацію.
