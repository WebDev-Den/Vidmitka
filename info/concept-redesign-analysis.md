# Аналіз переходу до публічного розкладу та єдиної адмін-панелі

## Статус і межі

Документ фіксує етап 1 задачі VID-029. Аналіз виконано без запуску тестів, build, браузерного QA, міграцій або запису в робочу базу даних. Поточний незавершений пакет VID-027 і його файли даних збережено окремо.

## Поточний стан

Застосунок уже має корисну основу:

- Next.js App Router із Server Components і Server Actions;
- Neon/PostgreSQL через `@neondatabase/serverless` та послідовні SQL-міграції;
- власну cookie-сесію, хешування пароля, блокування після невдалих входів і серверні перевірки ролей;
- довідники предметів, аудиторій, типів занять і пар;
- централізоване чергування тижнів і календар відпрацювань;
- публічний денний розклад і шкалу пар;
- компактний табличний стиль адміністративних форм.

Поточна концепція не відповідає новій у таких місцях:

| Область | Поточний стан | Потрібна зміна |
| --- | --- | --- |
| Доступ | Самореєстрація викладачів та адміністраторів, ролі `teacher` / `administrator` | Єдиний адміністратор без публічної реєстрації |
| Маршрути | `/sign-in`, `/sign-up`, `/dashboard/**` | Прихований вхід `/admin/login`, захищені `/admin/**` |
| Викладач | Одночасно обліковий запис і власник розкладу | Окремий довідник без права входу |
| Група | Група існує через студентів | Самостійний довідник розкладу |
| Заняття | Один викладач, одна аудиторія, без періоду дії | Кілька груп / викладачів / аудиторій, межі дії та активність |
| Винятки | Глобальна підміна дня через `makeup_days` | Окремі переноси, заміни, скасування й разові заняття |
| Імпорт | До 200 рядків, один викладач, без preview та idempotency | Адмінський JSON-імпорт 431+ записів із довідниками, preview, звітом і повторним імпортом |
| Публічний перегляд | Загальна сітка без вибору групи | День / тиждень за групою з відображенням винятків |
| Старий домен | Студенти, предмети викладача, журнал і відвідування | Вилучити з робочого UI та серверних сценаріїв після безпечного переходу |

## Ризики переходу

1. Поточна таблиця `lessons` має жорсткі зв’язки з `app_users`, `teacher_subjects`, однією аудиторією та exclusion-обмеженнями одного викладача. Її пряме розширення створить складну й ризикову міграцію.
2. SQL runner позначає міграцію після виконання всіх statement, але сам файл не обгорнутий в одну транзакцію. Нові міграції мають бути ідемпотентними; атомарність імпорту забезпечується окремою транзакцією прикладного модуля.
3. Видалення старих таблиць у тому самому релізі може втратити історію відвідування. Перехід має бути additive-first: створити нову модель, переключити код, експортувати / перевірити старі дані, і лише окремою явно дозволеною міграцією прибирати таблиці.
4. Приховування посилання на вхід не захищає `/admin`. Сесія та авторизація перевіряються сервером у layout, кожній Server Action і кожному адміністративному Route Handler.
5. Публічний розклад не повинен повертати email, hash, session або внутрішні дані адміністратора.
6. Наявні exclusion-обмеження не можуть безпосередньо описати кількох викладачів чи аудиторій. Конфлікти нової моделі треба перевіряти транзакційним доменним модулем і відповідними індексами / блокуванням.

## Рекомендована стратегія

Використати нову модель розкладу v2 поруч зі старими таблицями. Це дає чистий шов для `ScheduleRepository`, дозволяє імпортувати й перевірити дані без знищення чинного розкладу, а потім одним контрольованим кроком переключити публічний та адміністративний інтерфейси.

Головні глибокі модулі:

- `AdminSession`: вхід, сесія, вихід і серверна вимога адміністратора;
- `AcademicWeekCalendar`: один інтерфейс визначення першого / другого тижня;
- `ScheduleResolver`: формує фактичний розклад дати з базових записів і винятків;
- `ScheduleConflictChecker`: перевіряє зайнятість груп, викладачів та аудиторій;
- `TeacherScheduleImport`: аналізує, нормалізує, зіставляє й атомарно записує JSON;
- репозиторії довідників як адаптери доступу до даних.

## Поетапний план

1. **Модель v2:** додати довідники, зв’язки багато-до-багатьох, записи розкладу, винятки та журнал імпорту без видалення старих таблиць.
2. **Доменні модулі:** календар тижнів, resolver, conflict checker, parser / preview / commit імпорту. Підготувати тести на погоджених у VID-029 швах, але запуск відкласти до пакетного QA.
3. **Адмін-доступ:** прибрати реєстрацію з робочого маршруту, додати `/admin/login`, захищений `/admin/**`, ініціалізацію адміністратора через env / окрему команду.
4. **Адмін-інтерфейс:** розклад, групи, дисципліни, типи, аудиторії, викладачі, винятки, тижні й імпорт JSON.
5. **Публічний інтерфейс:** вибір групи, день / тиждень, інформація про поточний тиждень та винятки; без будь-якого посилання на вхід.
6. **Вилучення старої логіки:** прибрати сторінки та модулі студентів, журналу, викладацького кабінету й самореєстрації; старі таблиці поки зберегти як rollback-страхування.
7. **QA і release:** незалежний QA всього пакета, тестова міграція й імпорт на ізольованій БД; production-міграція та deployment лише після окремого дозволу.

## TDD-шви

Постійний дозвіл користувача на вибір швів застосовано. Тести перевірятимуть поведінку через такі інтерфейси:

- `analyzeTeacherScheduleJson(content)` — формат, mapping, нормалізація, дублікати й помилки;
- `buildImportPlan(analysis, existingCatalogs)` — створення / повторне використання сутностей та стабільні ключі;
- `resolveScheduleForDate(query)` — базові записи плюс перенесення, заміни, скасування й разові заняття;
- `getAcademicWeek(date, settings)` — понеділок як початок тижня, перехід через 7 днів і часовий пояс;
- серверні `requireAdministrator` та захищені дії — неавторизований доступ не змінює дані.
