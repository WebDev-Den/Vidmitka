# Vidmitka — розширений довідник агентів

## Мета проєкту

Vidmitka — український вебзастосунок для перегляду та керування розкладом навчальних занять. Під час розробки зберігайте українську локалізацію, простий академічний інтерфейс і чітке розмежування прав викладача та адміністратора.

## Технологічний стек

- Next.js 16 з App Router
- React 19
- TypeScript у строгому режимі
- Tailwind CSS 4
- shadcn/ui та Base UI
- pnpm
- GitLab CI/CD
- Vercel для preview і production deployment

Перед змінами в Next.js перевіряйте актуальні локальні інструкції в `node_modules/next/dist/docs/`.

## Навички Codex

Застосовуйте навички відповідно до задачі:

- `codebase-design` та `improve-codebase-architecture` — межі модулів і архітектурний рефакторинг.
- `vercel:nextjs` і `vercel:react-best-practices` — Next.js та React.
- `frontend-skill`, `web-design-guidelines` і `vercel:shadcn` — дизайн, доступність і UI-компоненти.
- `.agents/skills/qa-batch` — журнал запитів і незалежний пакетний QA за запитом або перед релізом.
- `.agents/skills/ui-spacing-review` — перевірка змін layout, CSS і TSX у фінальній QA-фазі, а не після кожної правки.
- `webapp-testing` і `playwright` — інструменти фінальної браузерної перевірки; `tdd` — поведінкові сценарії та публічні тестові межі, погоджені постійним дозволом користувача від 28.08.2026. Повторне погодження меж не потрібне; запуск перевірок залишається пакетним.
- `gitlab-ci-generator` і `gitlab-ci-validator` — GitLab pipeline.
- `vercel-deployment` і `vercel:deployments-cicd` — preview та production deployment.

Перед використанням навички повністю прочитайте її `SKILL.md`.

## Архітектурні правила

- Не накопичуйте сторінки, бізнес-правила, мок-дані та UI в одному файлі.
- Організовуйте код за функціональними областями: публічний розклад, заняття викладача, довідники, контроль конфліктів, ролі та автентифікація.
- Виносьте доменні типи й правила з React-компонентів.
- Відокремлюйте UI, прикладні сценарії та доступ до даних через чіткі інтерфейси.
- Використовуйте Server Components за замовчуванням; додавайте `'use client'` лише для локальної інтерактивності.
- Уникайте дублювання компонентів і CSS; розширюйте дизайн-систему через варіанти й токени.
- Не приховуйте помилки TypeScript і не використовуйте `ignoreBuildErrors` як постійне рішення.

## Якість і тестування

За домовленістю від 28.08.2026 основний агент реєструє задачі в [tasks.md](tasks.md) та реалізує пакет без тестування кожної зміни. Він не запускає автоматично build, тести чи браузерні огляди після окремої правки. Читання коду й перевірка безпечності diff залишаються частиною роботи.

За запитом на перевірку або перед дозволеним релізом **окремий QA-субагент** читає первинні запити, сам визначає тип і ризики, перевіряє пакет та оновлює журнал. Деталі, команди, критерії `PASS / FAIL / BLOCKED / NOT_RUN` й формат доказів — у [qa/process.md](qa/process.md). Основний агент не ставить собі незалежний `PASS`.

Завершення окремої відповіді не запускає QA. До фінального прогону допустимий статус «Реалізовано; QA очікується». Наявні CI/Vercel gates не вимикаються.

## Доступність і UX

### Незмінний дизайн

Для кожної UI-задачі обов’язково застосовуйте правила з `info/design-system.md`. Початковий бірюзовий логотип, теплий фон, світлі поверхні, темна типографіка та бірюзовий primary-акцент не можна замінювати без прямого погодження користувача. Канонічні файли логотипа: `components/brand-mark.tsx` і `public/icon.svg`.

- Усі поля форми повинні мати доступну назву.
- Icon-only кнопки повинні мати `aria-label`.
- Модальні вікна повинні підтримувати Escape, focus trap і повернення фокусу.
- Заявлені клавіатурні скорочення мають бути реалізовані та протестовані.
- Стан навігації, фільтрів і вкладок, який потрібно поширювати або відновлювати, зберігайте в URL.
- Поважайте `prefers-reduced-motion` і не вимикайте масштабування сторінки.

## GitLab CI/CD і Vercel

Production deployment та push у `main`, який запускає Vercel, дозволені лише після актуального `PASS` незалежного QA і успішних обов'язкових перевірок. Це не замінює дозвіл користувача на публікацію.

Очікувана послідовність pipeline:

1. Встановлення залежностей через frozen lockfile.
2. TypeScript typecheck.
3. Lint.
4. Unit та integration тести.
5. Production build.
6. Playwright smoke/E2E-тести.
7. Vercel production deployment лише для захищеної гілки `main`.

Vercel deploy job повинен залежати від тестових jobs через `needs`. Використовуйте захищені й masked GitLab variables: `VERCEL_TOKEN`, `VERCEL_ORG_ID` і `VERCEL_PROJECT_ID`. Не записуйте секрети у файли репозиторію або логи pipeline.

Для merge request використовуйте окреме preview-середовище. Preview deployment не повинен отримувати production-секрети або доступ до production-бази даних.

## Definition of Done

Реалізація без фінального QA фіксується як «Реалізовано; QA очікується», а не як протестована. Пакет готовий до дозволеного релізу, коли:

- реалізована запитана поведінка;
- typecheck, lint, тести та build проходять;
- основний сценарій перевірений у браузері;
- немає нових помилок або warning у консолі;
- UI доступний з клавіатури та адаптивний;
- документація й CI/CD оновлені, якщо змінився процес запуску або deployment;
- у diff немає секретів, випадкових generated-файлів або сторонніх змін.
- окремий QA-агент зафіксував актуальний звіт і результати всіх задач пакета в журналі.
