# Vidmitka — інструкції для агентів

## Область дії

Цей файл застосовується до всього репозиторію. Vidmitka — український вебзастосунок для перегляду та керування розкладом навчальних занять. Зберігайте українську локалізацію, простий академічний інтерфейс і чітке розмежування прав викладача та адміністратора.

## Технологічний стек

- Next.js 16 з App Router
- React 19
- TypeScript у строгому режимі
- Tailwind CSS 4
- shadcn/ui та Base UI
- pnpm
- GitLab CI/CD
- Vercel для preview і production deployment

Перед змінами в Next.js перевіряйте актуальну документацію, доступну в `node_modules/next/dist/docs/`.

## Робочий процес

1. Перед редагуванням перевірте `git status` і не перезаписуйте сторонні зміни.
2. Проаналізуйте наявну архітектуру та використовуйте чинні компоненти, стилі й токени.
3. Для функцій або виправлень, де це практично, працюйте за циклом red → green → refactor.
4. Після змін виконайте перевірки, пропорційні ризику.
5. Для UI перевірте основний сценарій у реальному браузері на desktop, tablet і mobile.

Усю проєктну аналітику, архітектурні описи, моделі даних, плани та тестові сценарії зберігайте в `info/` і додавайте до `info/README.md`. Службовими винятками є кореневий `AGENTS.md` і проєктні Codex skills у `.agents/skills/`, оскільки їхнє розташування потрібне для автоматичного застосування правил.

Використовуйте релевантні Codex skills: `codebase-design`, `vercel:nextjs`, `vercel:react-best-practices`, `frontend-skill`, `web-design-guidelines`, `vercel:shadcn`, `tdd`, `webapp-testing`, `playwright`, `gitlab-ci-generator`, `gitlab-ci-validator`, `vercel-deployment` і `vercel:deployments-cicd`. Перед використанням skill повністю прочитайте його `SKILL.md`.

Після змін layout, CSS або TSX обов'язково застосовуйте проєктний skill `ui-spacing-review` із `.agents/skills/ui-spacing-review/SKILL.md`. Він перевіряє систему відступів, вирівнювання, щільність, overflow і адаптивний ритм на 1440, 820 та 390 px.

## Архітектура та код

- Не накопичуйте сторінки, бізнес-правила, мок-дані та весь UI в одному файлі.
- Організовуйте код за функціональними областями: публічний розклад, заняття викладача, довідники, контроль конфліктів, ролі та автентифікація.
- Виносьте доменні типи й правила з React-компонентів.
- Відокремлюйте UI, прикладні сценарії та доступ до даних через чіткі інтерфейси.
- Використовуйте Server Components за замовчуванням; додавайте `"use client"` лише для інтерактивності.
- Для стану використовуйте похідні значення замість дублювання даних у `useState` та `useEffect`.
- Оновлюйте масиви й об'єкти незмінно, використовуючи функціональний `setState`, коли нове значення залежить від попереднього.
- Уникайте дублювання компонентів і CSS; розширюйте дизайн-систему через варіанти й токени.
- Не приховуйте помилки TypeScript і не використовуйте `ignoreBuildErrors` як постійне рішення.
- Не додавайте нову залежність, якщо задачу можна зрозуміло вирішити наявним стеком.

## UI, локалізація та доступність

### Незмінний візуальний канон

- Перед будь-якою UI-зміною прочитайте `info/design-system.md` і звірте результат із затвердженим початковим дизайном «Журнал занять».
- Використовуйте лише початковий логотип: бірюзовий округлений аркуш із темною галочкою, згином і світлою крапкою. Джерела істини — `components/brand-mark.tsx` та `public/icon.svg`.
- Не замінюйте логотип готовою іконкою, літерним знаком, синім квадратом або альтернативною версією без прямого запиту користувача.
- Основна палітра: теплий фон `#F5F2EB`, білі поверхні, текст `#18283D` / `#243B3A`, muted `#71807B`, межі `#DED9CD`, primary `#0F766E`, фірмовий бірюзовий `#48C5B5`.
- Синій дозволений лише для малих другорядних тегів та аватарів. Не використовуйте його як primary. Не додавайте фіолетову палітру, декоративні градієнти або темну sidebar без прямого погодження.
- Зберігайте світлі topbar/sidebar, теплу робочу область, тонкі межі, слабкі тіні та стримані радіуси `8–14px`.

- Усі користувацькі тексти мають бути українською, якщо задача не вимагає іншого.
- Використовуйте термін «заняття», а не «урок», у журналі викладача.
- Усі поля форми повинні мати доступну назву.
- Icon-only кнопки повинні мати `aria-label`.
- Модальні вікна повинні мати коректну роль, назву, закриття через Escape, focus trap і повернення фокусу.
- Інтерактивні елементи мають працювати з клавіатури й показувати `:focus-visible`.
- Поважайте `prefers-reduced-motion`; не вимикайте масштабування сторінки.
- Не допускайте горизонтального переповнення сторінки. Великі таблиці можуть прокручуватися лише у власному контейнері.
- Мінімально перевіряйте ширини 1440 px, 820 px і 390 px.
- Для кожної зміни відступів фіксуйте фактичні browser-вимірювання та перевіряйте їх через `ui-spacing-review`.

## Перевірки

Обов'язковий мінімум перед завершенням задачі:

```powershell
pnpm exec tsc --noEmit
pnpm build
```

У `package.json` поки немає окремих команд `lint` і `test`. Після додавання відповідного стеку запускайте також lint, unit/integration та Playwright E2E-тести. Для змін UI перевірте:

- основний user flow;
- адаптивність;
- клавіатурну навігацію;
- browser console без нових errors і warnings;
- відсутність document-level horizontal overflow.

## GitLab CI/CD і Vercel

Production deployment дозволений лише після успішного проходження всіх обов'язкових перевірок. Очікувана послідовність pipeline:

1. Встановлення залежностей через frozen lockfile.
2. TypeScript typecheck.
3. Lint після додавання lint-скрипта.
4. Unit та integration тести після додавання тестового стеку.
5. Production build.
6. Playwright smoke/E2E-тести.
7. Vercel production deployment лише для захищеної гілки `main`.

Vercel deploy job повинен залежати від усіх тестових jobs через `needs` і не запускатися після невдалих перевірок. Використовуйте захищені та masked GitLab variables: `VERCEL_TOKEN`, `VERCEL_ORG_ID` і `VERCEL_PROJECT_ID`. Не записуйте секрети у файли репозиторію, артефакти або логи pipeline.

Для merge request використовуйте окреме preview-середовище. Preview deployment не повинен отримувати production-секрети або доступ до production-бази даних.

## Git-гігієна

- Не робіть destructive git-операцій без явного запиту користувача.
- Не комітьте `.next/`, `.playwright-cli/`, `*.tsbuildinfo`, локальні env-файли або секрети.
- Не змінюйте lockfile без зміни залежностей.
- Не змішуйте задачу з непов'язаним форматуванням або рефакторингом.

## Definition of Done

Задача завершена, коли:

- реалізована запитана поведінка;
- typecheck і production build проходять;
- доступні lint і тести проходять;
- основний сценарій перевірений у браузері, якщо змінено UI;
- немає нових помилок або warnings у консолі;
- UI доступний з клавіатури та адаптивний;
- документація й CI/CD оновлені, якщо змінився процес запуску або deployment;
- у diff немає секретів, випадкових generated-файлів або сторонніх змін.
