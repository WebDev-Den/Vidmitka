# План розробки системи керування розкладом

## 1. Мета плану

План розбиває роботу на функціональні етапи. Кожний етап завершується перевірюваним результатом і не залежить від вибору технологій або способу реалізації.

Позначення стану:

- `[ ]` — не розпочато;
- `[~]` — виконується;
- `[x]` — завершено та прийнято.

## 2. Послідовність етапів

Стан: `[~]`

Результати:

- [x] визначено дві ролі: викладач і адміністратор;
- [x] зафіксовано права кожної ролі;
- [x] описано обов'язкові дані заняття;

- [ ] погоджено перелік навчальних днів;

Критерій завершення: усі відкриті бізнес-рішення погоджені власником продукту.

- адміністратор керує всіма довідниками;
- неактивні сутності не доступні для нового заняття;
- чинні зв'язки не втрачають зрозумілості після деактивації довідника.
- викладач керує лише студентами у власних предметних списках;
- прибирання студента з предмета не видаляє саму сутність студента.

### Етап 2. Перегляд розкладу

Стан: `[ ]`

Функціональний обсяг:

- загальний тижневий розклад;
- впорядкування за днями та парами;
- перемикання чисельника, знаменника й обох тижнів;
- фільтри за викладачем, предметом, аудиторією та днем;
- окремий перегляд «Мої заняття» для викладача;
- перегляд деталей заняття.

Критерії приймання:

- обидві ролі бачать однаковий актуальний загальний розклад;
- «Мої заняття» не містить занять інших викладачів і позначає адміністративно створені заняття як доступні лише для перегляду;
- заняття «обидва тижні» показується і для чисельника, і для знаменника;
- порядок днів і пар є стабільним та однозначним.

### Етап 3. Створення заняття

Стан: `[~]`

Функціональний обсяг:

- форма створення заняття;
- вибір предмета, аудиторії, дня, пари й типу тижня;
- автоматичне призначення поточного викладача для ролі викладача;
- вибір викладача адміністратором;
- перевірка обов'язкових значень і активності довідників;
- зрозумілий результат успіху або відмови.
- [x] пакетний імпорт власного розкладу викладача з JSON і CSV;
- [x] завантажувані приклади обох форматів;
- [x] атомарна перевірка активних довідників і конфліктів перед імпортом;
- [x] відображення імпортованих занять у розділі «Мої заняття».

Критерії приймання:

- викладач не може створити заняття від чужого імені;
- предмет, аудиторія та пара вибираються лише з підготовлених переліків;
- неповне або недопустиме заняття не додається до розкладу;
- успішно створене заняття відразу з'являється у відповідних переглядах.
- некоректний імпорт не створює частково збережених занять;
- викладач не може вказати іншу особу власником імпортованих занять.

### Етап 4. Перевірка конфліктів

Стан: `[ ]`

Функціональний обсяг:

- єдина матриця перетину типів тижня;
- перевірка зайнятості аудиторії;
- перевірка зайнятості викладача;
- показ усіх знайдених конфліктів;
- повторна перевірка перед остаточним збереженням.

Критерії приймання:

- чисельник не конфліктує зі знаменником за інших однакових умов;
- «обидва тижні» конфліктує з чисельником і знаменником;
- одна аудиторія не може мати два заняття в одному слоті;
- один викладач не може мати два заняття в одному слоті;
- різні день або пара усувають конфлікт;
- повідомлення називає тип конфлікту та конфліктне заняття.

### Етап 5. Редагування та видалення заняття

Стан: `[ ]`

Функціональний обсяг:

- редагування власного заняття викладачем;
- редагування будь-якого заняття адміністратором;
- повна повторна перевірка після редагування;
- виключення поточного заняття з самоперевірки;
- підтвердження видалення;
- оновлення всіх переглядів після зміни.

Критерії приймання:

- викладач не може змінити або видалити чуже чи створене адміністратором заняття;
- адміністратор може змінити або видалити будь-яке заняття;
- редагування не дозволяє створити конфлікт;
- скасування форми або підтвердження видалення не змінює розклад;
- видалене заняття не відображається як чинне.

### Етап 6. Навчальний період і календарна логіка

Стан: `[~]`

Функціональний обсяг:

- визначення меж навчального періоду;
- [x] адміністратор задає будь-яку дату тижня-чисельника;
- [x] послідовне чергування чисельника й знаменника;
- [x] визначення типу конкретного календарного тижня;
- [x] попередній розрахунок у формі та збереження точної дати без зсуву часового поясу;
- [x] сумісність із попереднім налаштуванням опорного знаменника;
- [x] перевірки неділі/понеділка, переходу року, високосної дати та київського часу;
- [x] завершення семестру з підтвердженим очищенням занять;
- контроль неоднозначних або перекривних періодів.

Критерії приймання:

- для будь-якого тижня чинного періоду визначається рівно один тип;
- сусідні тижні мають різні типи;
- завершення одного періоду не змінює історичне значення попередніх тижнів;
- користувач бачить, за яким типом тижня сформовано розклад.
- після завершення семестру всі заняття видалені, а студенти та їхні предметні зв'язки збережені.

### Етап 7. Адміністративний контроль актуальності

Стан: `[ ]`

Функціональний обсяг:

- перелік конфліктних занять;
- перелік занять із неактивними викладачами;
- перелік занять із неактивними предметами, аудиторіями або парами;
- перехід від проблеми до редагування заняття;
- повторна перевірка після виправлення.

Критерії приймання:

- адміністратор бачить усі відомі проблеми розкладу;
- кожна проблема має зрозумілу причину;
- виправлена проблема зникає після повторної перевірки;
- система не вносить непідтверджених автоматичних змін.

### Етап 8. UX, доступність і адаптивність

Стан: `[~]`

Функціональний обсяг:

- зрозумілі помилки перевірки;
- коректна робота загального розкладу, форм і таблиць на великих, середніх і малих екранах;
- підтвердження небезпечних дій.

Критерії приймання:

- основні сценарії виконуються без миші;

- користувач розуміє, чому заняття не вдалося зберегти.

### Етап 9. Функціональне приймання та готовність до випуску

Стан: `[ ]`

Функціональний обсяг:

- перевірка всіх прав ролей;
- перевірка позитивних і негативних сценаріїв заняття;
- перевірка повної матриці типів тижня;
- перевірка конфліктів викладача та аудиторії;
- перевірка довідників і деактивації;
- перевірка актуальності документації.

Критерії приймання:

- жодна роль не отримує зайвих прав;
- конфліктний розклад неможливо зберегти;
- загальний і персональний перегляди узгоджені;
- документація відповідає фактичній поведінці системи;
- немає невирішених критичних функціональних дефектів.

## 3. Мінімальний перший випуск

До мінімального першого випуску входять:

- дві ролі та їх права;
- довідники викладачів, предметів, аудиторій і пар;
- студенти та списки студентів за предметами викладачів;
- загальний розклад і «Мої заняття»;
- створення, редагування та видалення занять;
- імпорт власного розкладу викладача з JSON або CSV;
- чисельник, знаменник та обидва тижні;
- блокування конфліктів викладача й аудиторії;
- адміністративний контроль актуальності;
- завершення семестру зі збереженням студентів;
- адаптивний і доступний основний інтерфейс.

Функції поза цим переліком мають оформлюватися окремими вимогами й не повинні непомітно розширювати перший випуск.
