# VID-064 — імпорт, експорт і dry-run

## Інтерфейс

Візуальна теза: компактний академічний інструмент на білому / теплому фоні з одним бірюзовим акцентом. План вмісту: експорт актуальних даних → вибір файлу → таблиця dry-run → окреме підтвердження. Взаємодія: native focus/hover, правдивий pending, поява підсумку без декоративних анімацій; зміна файлу прибирає старе підтвердження.

`/admin/import` має кнопку «Експортувати JSON», завантаження файлу, «Перевірити без збереження (dry-run)» та окрему «Підтвердити та імпортувати». Експорт — захищений сесією approved administrator GET `/admin/import/export`, `no-store`, attachment; відсутність сесії повертає на login. Помилка завантаження показується на сторінці.

Файл зберігається в стані форми між dry-run та підтвердженням: React form reset не втрачає завантажений File. Після нового вибору старий підсумок приховано. На сервері повторно перевіряються SHA-256 файла, результат preview, права й обмеження. Ліміт — 3 МБ, щоб multipart залишався нижче ліміту Vercel; нових секретів або міграцій не потрібно.

## Формат

Експорт `vidmitka-schedule-YYYY-MM-DD.json`: об’єкт `format: "vidmitka-schedule"`, `version: 1`, `exportedAt`, `data`.

`data` містить масиви `groups`, `teachers`, `disciplines`, `rooms`, `lessonTypes`, `periods`, `entries`, `exceptions`, `calendar`, `weeks`. Це всі поточні збережені дані розкладу, включно з неактивними й майбутніми записами, а не лише заняття вибраного дня. Відвідуваність, паролі, облікові записи, push-підписки, секрети, історія запусків крону не експортуються.

Схема/allowlist — `lib/schedule-transfer/schema.ts`. ID UUID зберігаються; пари зв’язуються за унікальним номером, а не внутрішнім identity ID бази. Заняття / виняток містять повні `group_ids`, `teacher_ids`, `room_ids`; їх зміна замінює лише зв’язки цього запису. Календарний `version` не переноситься: при оновленні сервер збільшує власну версію. Actor ID призначається сервером, не з файла. Збережено source-ідентифікатори для сумісності зі старим імпортом.

Імпорт об’єднує дані за ID (пари — за номером, календар — за датою). Записи поза файлом залишаються. Це **не destructive restore** усієї БД. Невідомі поля, розділи, версії, повторні ID, некоректні дати / час / кольори та відсутні зв’язки відхиляються. Однакова нормалізована назва з іншим ID — помилка, а не автоматичне небезпечне злиття.

Старий масив teacher-schedule підтримується через чинний parser / transactional repository. Новий REST API VID-063 поки має власний старий формат `/imports/*`; native snapshot тут належить admin UI і не підміняє контракт API.

## Dry-run і транзакція

Dry-run виконує тільки readonly Repeatable Read вибірку та pure-планування об’єднаного стану: створення / оновлення / незмінені записи за розділами, унікальні назви, FK, власний час, періоди дії, перетини активних пар, базові правила винятків, захищені журналом дати. Нові recurring-конфлікти груп / викладачів / аудиторій показані як попередження й потребують checkbox-підтвердження. Не створюються audit rows, не рухаються sequence, не пишуться тимчасові записи. Це попередня валідація, а не гарантія успіху за майбутнього стану БД; остаточні SQL constraints залишаються чинними.

Native commit повторює планування; fingerprint захищає від змін після preview. Одна транзакція блокує schedule-таблиці та attendance_sessions, звіряє актуальні дані під lock, повторно перевіряє адміністратора й журнал; далі upsert лише змінених записів, заміна їх зв’язків і один audit run. Конкурентна зміна, FK/unique/check або lock timeout скасовують весь запис. Переноси з журналами не можна обійти імпортом. Незмінені записи не переписуються. Period identity може мати звичайні пропуски при невдалому commit; dry-run його не змінює.

## Межі тестів і черга QA

Постійний дозвіл TDD-меж згідно з AGENTS застосовано без повторного погодження: публічні pure `parseSnapshot` / `planSnapshot`, серверний сценарій export → preview → commit → export в ізольованій БД, HTTP export auth та форма через браузер. Тести готуються разом із кодом; red → green не заявляється й запуск відкладено за qa-batch.

- Unit: round-trip, невідомі поля / версія / повторні ID, дати, FK, перетини, journal lock, незмінені записи та відсутність мутації вхідних об’єктів.
- DB: експорт не містить секретних таблиць; preview не змінює export; round-trip без дублів; upsert / memberships / calendar version; stale preview; відмова не лишає часткового імпорту. Використати існуючий ізольований QA schema harness, не production.
- Підготовлена команда DB-перевірки: `pnpm test:schedule-transfer-integration` (не запускалася).
- UI: export filename/error, вибір файлу, двофазне застосування, повторний вибір того самого і іншого файла, warnings checkbox, malformed/empty/oversize, session expiry; 1440/820/390, keyboard/focus, console, overflow та spacing review окремим QA-агентом.
- Фінальний пакет VID-063/064: typecheck, tests, isolated DB integration, build, UI QA. На етапі розробки нічого з цього не запускалося; `NOT_RUN`.
